# Issue 5212 — [QA Testing] LW 53.1 Lan procs not starting

[View on GitHub](https://github.com/lightriversoftware/netflex/issues/5212)

## Summary

After installing the `53.132` patch (release 5.3.1, build 32) on host `linc10vm15`, **none of the LAN processes would start**. Manual restart attempts by the reporter and by Gavin both failed, so Dan Nuzzo was pulled in. Nuzzo rebooted the APP (to turn up trace on `m_sdi`); when the app came back, the LAN procs started normally.

Dan's working theory is that something in the code caused the system to believe the LAN processes were **already up**, so the startup path silently skipped launching them. He asked for this issue to be opened and pointed at `make_sure_no_dups(int frmlnk_pid, int neid, int protect, int restarted)` as the suspect.

## Reproduction Steps

1. On a 5.3.1 system with LAN procs running, install the `53.132` patch (which kills/replaces the per-NE LAN processes but leaves the long-running `m_sdi` daemon up).
2. Observe that the LAN procs do not come back up.
3. Attempt to start them manually — they still won't start.

## Observed Behavior

- No LAN processes start after the patch install.
- In-place / manual restarts do not recover them.
- Only a **full APP reboot** (restarting `m_sdi`) brings the LAN procs up.
- System behaves as though the LAN processes were already running (phantom "already up" state).

## Resolution / Notes

No human/verified resolution posted yet.

An **automated, DRAFT/UNVERIFIED RCA** was posted by `netflex-workflow-bot` on 2026-06-24 (MEDIUM confidence — do not act on without engineer review). Summary of its findings:

> **Mechanism — stale in-process `ps` cache produces phantom duplicates**, so the spawn path silently skips starting every LAN proc.
>
> - `start_neproc` (in `cnc/sdi/src/m_sdi.c`, ≈ line 937) returns `SUCCESS` *before forking* whenever `make_sure_no_dups` reports a duplicate, and `test_interface` similarly marks the NE `NE_MODIFIED(fptr, NO_LINK_PRIV)` instead of relinking. A false "duplicate" verdict therefore means the LAN proc never (re)starts.
> - When `NewPidCheck==1`, the dup decision is made against a **static, process-lifetime cache** (`_pidmap`) in `cnc/utility/src/cpputil.cpp` (`checkLanPidWk`). The check is a pure cache lookup — it never verifies the cached PID is actually alive (no `kill(pid, 0)` / `/proc/<pid>` liveness check, no eviction of dead entries).
> - The retry/reload safety net calls the **non-forcing** `loadPidMap()` (`loadPidMapWk(0)`), which only re-reads `ps` when the map is empty, `force` is set, or the TTL (`PSCACHE_RELOAD`, default 300s) has expired — so a stale-but-not-expired map is re-evaluated unchanged.
> - The `restarted` flag that was meant to defeat exactly this case is **plumbed through but ignored** — it appears only in signatures and the pass-through recursive call, never in any condition, and `start_neproc` hard-codes `restarted=0` at its call site.
>
> **Why the patch triggers it and a reboot cures it:** the patch kills the LAN procs but leaves `m_sdi` running, so its static `_pidmap` still holds the pre-patch (now-dead) LAN PIDs. Every restart within ~5 min sees a cached entry with a dead PID that differs from the new `frmlnk_pid` → phantom DUP → start declined. An APP reboot restarts `m_sdi`, so `_pidmap` starts empty and force-loads a fresh snapshot — the observed recovery.
>
> **Recommended fix (both in `cnc/utility/src/cpputil.cpp`):** (1) force a fresh snapshot (`loadPidMapWk(1)`) when the caller signals `restarted`, and pass `restarted` through from `start_neproc`; (2) validate the candidate PID with `kill(pid, 0)`/ESRCH before declaring a duplicate and evict dead cache entries. (3, belt-and-suspenders) force a reload on the bottom retry when a dup was found on the first pass. Rebuild the utility lib containing `cpputil.o` and `m_sdi`, then restart `m_sdi`.
>
> **Operational mitigation until patched:** after any LAN-affecting patch install, reboot the APP (restart `m_sdi`) rather than relying on in-place LAN restarts; or lower `PSCACHE_RELOAD` to shrink the stale window.

The bot also flagged this as the complementary half of the same stale-`_pidmap` family previously addressed by the `loadPidMapWk` TTL fix (see related knowledge-store items #4835 / PR #5171 and #5083 / PR #5126).
